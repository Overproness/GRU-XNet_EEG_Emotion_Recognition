## Required pre-freeze resource correction

The initially reviewed protocol claimed a twenty **CPU/wall-minute** cap. The worker initially checked only `time.monotonic()` elapsed wall time. With twelve BLAS threads, wall and process CPU times can differ. The declaration must either implement both budgets and report both, or explicitly declare a wall-only cooperative cap before freezing. This is an implementation/description mismatch, not permission to expand sample access.

The initial reader also checked time before original-file hashing but not immediately before the selective read. A slow full-file integrity check could therefore cross the cap before a new decode started. Add a cap check immediately before the selective read and preferably between raw-file hashing chunks. A Python budget check cannot interrupt a running native operator instantaneously; its cooperative scope must remain explicit. Prevent new work after the next exceeded-budget check rather than claim a hard process watchdog that does not exist.

Any such pre-execution correction must update bound code/protocol hashes, preserve the superseded declaration and record why it changed. Neither a correction nor the initial failed declaration is a pilot retry because no recording range has yet been decoded.

The first declaration's `KeyError` came from assuming a top-level receipt `passed` field. The corrected worker checks the actual plan hash, 2,940 source ranges, 980 late identities, twenty-four pilot rows and explicit zero-access fields. This schema correction changes no scientific setting.
